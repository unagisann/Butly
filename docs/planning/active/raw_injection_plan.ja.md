## 1. きっかけ: 評価が目的化していた

直近の作業は測定器の整備に偏っていた（公式互換 Token F1 の系統誤差、Semantic Judge の
経路差、反転率、ノイズ床）。必要ではあるが、検索も想起も改善していない。
そこで「検索・想起の実課題は何か」を数え直したところ、**前提が間違っていた**ことが分かった。

## 2. 失敗の内訳を取り直した

`analyze-evidence` を現行 corpus（1,105カード・全1,986問）で回した結果。
これまで参照していた内訳は v31（conv-26 の199問・qwen 製107カード）のもので、**順位が逆だった**。

| 落ちた場所 | v37 (注入3枚) | v39 (注入10枚) | 効く打ち手 |
|---|---:|---:|---|
| **根拠を含むカードが無い** | **210（42.2%）** | **210（56.6%）** | カード化 / provenance |
| 候補 top20 に入らない | 115（23.1%） | 115（31.0%） | embedding / 検索クエリ |
| 候補には居るが注入枠の外 | 173（34.7%） | 46（12.4%） | ランキング / 注入枠 |
| 検索が走っていない | 0 | 0 | — |
| **evidence=0 合計** | **498** | **371** | |

母数は cat5 を除く 1,536問。

### 2.1 ここで一番重い事実

top-3 → top-10 で **127問に新しく根拠が届いた**（evidence=0 が 498→371）。
それなのに**公式互換は +0.0088、cat1-4 でも +0.0152 しか動かなかった**。

さらに、**根拠がすでに届いている994問のうち189問（19%）は0点**である。
正解の発話がプロンプトに入っていても2割は外す。

> **根拠を届けることと、答えられることは別。** 検索側の改善は、この換算率で割り引いて
> 期待値を置く必要がある。

**この割り引き方は後に v41 Oracle Reader で精緻化した。§7.2.2 を参照。** 換算率は
「根拠が届いたか」の二値ではなく、全件被覆と部分被覆を分けて出す（42.5% / 27.4%）。
両層は質問難度も異なるため、完全性を唯一の原因とはしない。また実注入ベースで原文が
全件届いた833問のSemanticは0.859で、この選択済み部分集合ではRAW3 bundleの明確な害は
見えなかった（§7.2.1）。

## 3. `no_card` 210問の正体

「カードに事実が無い」と分類された問題を、archive の原文と突き合わせた。

| | 問数 |
|---|---:|
| `no_card` 判定（cat5 込み） | 279 |
| ├ うち official ≥ 0.5（実際は答えている） | 92（33%） |
| evidence の発話が archive に残っている | **272 / 279（97.5%）** |
| ├ **注入されたカードと同じ日の RAW に在る** | **178** |
| └ その日のカードが注入されていない | 94 |
| **archive にも無い＝本当の欠落** | **7** |

`no_card` は「gold evidence のファイルと `source_files` が重なるカードが無い」という
**ファイル粒度の近似**であって、事実がどこにも無いという意味ではない。
RAW 保存層まで含めて回収不能なのは7問だった。一方、カード本文から落ちた事実の量は
別途意味的に測る必要があり、この7問をそのまま「カード化による欠落」とは扱わない。

実際に8問読んだ結果も同じ方向だった。`conv-30_qa_043` は「regionals で1位を取った」は
カードに残り、演目名 "Finding Freedom" だけが要約で落ちている。しかしその発話は
`session_20230120_160400_000000_009.json` に原文のまま残っている。

## 4. RAW がどう配線されているか

```
knowledge_cards.source_files  →  発話単位の archive ファイル（1〜2個/カード）
knowledge_cards.raw_reference →  "2023-01-20_raw_combined"（日単位のラベル・未使用）
                ↓
resolve_raw_reference(candidates, top_k=rag_raw_top_k)
                ↓
  カードのスコア順に source_files を集め、文字数予算に入るだけ greedy
```

- **`rag_raw_top_k` の既定は 1**。つまり**最上位カード1枚ぶんの原文しか展開していない**。
- 実測: 注入 RAW は平均 **1.94ファイル / 671文字**。`rag_raw_max_chars` は **2,500**。
  **予算の 27% しか使っていない。**
- **RAW 本文の関連度は一度も見ていない。** 並び順はカードのスコア順、表示は時系列順。

### 4.1 passage リランクは「計算済みで捨てている」

`EvidenceFusion.rerank()` はカードごとに Episode と **RAW チャンク（1,800字刻み）** を
ユニット化し、全ユニットを埋め込んで質問との cosine を取り、**MaxP の勝者**を選んでいる。
勝ったユニットの `evidence_type` と **`source_file` は `evidence_fusion_scores` に記録済み**。

**この勝者情報を注入側は使っていない。** カードの順位付けに使って捨て、RAW は別ロジック
（カード順）で選び直している。

## 5. 「同じ量で入れ替える」は負ける

`evidence_fusion_scores` を使って、注入量を変えずに RAW を passage スコア順へ
置き換えた場合を模擬した（1,974問）。

| | evidence 命中 | 注入ファイル数 |
|---|---:|---:|
| 現行（1位カードの原文を全部） | 994（50.4%） | 1.94 |
| passage スコア順に同数だけ | **792（40.1%）** | 1.93 |

内訳は維持 631 / 取りこぼし 363 / 新規 161 = **差し引き -202問**。

**理由**: 現行は1位カードの `source_files` を*連続した発話ファイルごと*渡している。
正解は「質問に最も似た1チャンク」ではなく**その隣の発話**にあることが多い。
`conv-30` の例（カードは `_008`、正解は `_009`）がそれで、passage 単位で最良を1つ選ぶと
近傍が切れる。**会話ログでは「最も似た断片」より「近傍ごと」のほうが当たる。**
通常の passage retrieval の定石と逆であり、この点は記録しておく価値がある。

### 7.2 伸びしろを段階別に割り当てる

v41との差を、どの失敗段階の問へ集中しているかという診断値として割り当てる。
cat1-4の1,531問（provenanceを解決できた問）を、**gold evidenceの原文が実際にpromptへ
入ったか**で排他分類する。判定は段階1〜3が`analyze-evidence`と同じ指標
（`search_executed` / `oracle_available` / `recall_at_20` / `recall_at_3`）、
段階4〜6が`diagnostics.rag.raw_reference.files`とgold evidenceファイルの突き合わせである。
表はSemantic normalized scoreで、寄与率は全層の純差への診断的な配分である。各段階だけを
修正した介入実験ではないため、施策で回収できる因果的な割合とは解釈しない。

### 7.2.1 §4〜§6を見直す: 完全被覆層ではbundleの明確な害はない

§4〜§6は「RAWの渡し方（`rag_raw_top_k`、passageスコア順、近傍bundle）」を改善余地として
扱ってきた。v41は、少なくとも完全被覆できた層ではRAW3 bundleの明確な害がないことを示す。

原文が全件届いた833問では、v40の0.859がv41の0.832を上回った（対応ありt=-2.06）。
ただしこの部分集合はcat4が541問で、必要evidenceも平均1.12ターンと少ない。6層比較の
多重性も踏まえると、「余分な発話は利益」「渡し方は解決済み」と断定する強さはない。

したがって近傍bundleはprovenance・ランキングより後に置くが、未検証のまま閉じない。
goldターンと必要近傍を固定するOracle Bundleを一度比較し、exact-turn Oracleとの差を分離する。

段階5「一部しか届かない」196問（診断寄与15%）は154問がcat1で、必要evidenceが平均
3.50ターンあり、量不足は有力である。ただし近傍の選び方・提示形式との影響分離は未実施なので、
**multi-hop問で必要ターンを揃えきること**を主仮説としてOracle Bundleで確認する。

### 7.2.2 §2.1 を修正する: 換算率は完全性別に測る

§2.1では「根拠を届けることと答えられることは別。検索側の改善はこの換算率で割り引いて
期待値を置く必要がある」と書いた。二値coverageだけでは割り引き方が粗かった。

v37→v40で原文が新しく届いた215問を、届いた完全性で割る（公式互換ベース）。

| | 問数 | 改善 | 換算率 |
|---|---:|---:|---:|
| **全件届いた** | 153 | 65 | **42.5%** |
| 一部だけ届いた | 62 | 17 | 27.4% |

**「根拠が届いた」を二値で数えると換算率を過小評価し得る。** §7の27.3%は
`evidence_coverage`（カードの`source_files`基準で、部分被覆を含む）で数えた値である。
実注入ベースで全件揃った層に限れば42.5%になる。ただし両層は質問難度も異なる非ランダムな
部分集合なので、この差だけから完全性を唯一の原因とはしない。

> **今後「新規カバー→回答改善の換算率」を出すときは、部分被覆と全件被覆を必ず分ける。**
> 二値のcoverageで割った換算率は、施策の効果を過小評価する方向に偏る。

なおv41のevidence=0層の換算率（63.9%）とこの42.5%を直接並べてはいけない。前者は
「v40が届けられなかった502問」、後者は「RAW3が届けられた215問」で母集団が排他であり、
差を届け方の優劣へ帰属できない。**比較できるのは同一母集団の段階別診断値（§7.2の表）である。**

### 7.3 gold-evidence-only条件の観測失敗率は17%

gold根拠だけを直接渡した条件のcat1-4は0.6258（Semantic 0.7753）だった。
1,540問のうち262問（17.0%）はSemanticで`incorrect`のままである。ただしこの262問には、
不完全なgold注記、近傍文脈を除いた影響、cat3の外部知識、Judge誤差も入り得る。

したがって17.0%は純粋な`utilization_miss`の床ではなく、現行readerのgold-evidence-only条件に
おける観測失敗率である。v40との差+0.17は検索・通常注入側の改善余地を置く基準として使うが、
固定された回収上限にはしない。Oracle Bundleを追加してreaderとcontext不足をさらに分ける。

### 7.4 cat5は読解基準から外し、棄権リスクとして残す

| cat5（446問） | v40 RAW3 | v41 Oracle |
|---|---:|---:|
| 「情報なし」と答えた | 262（58.7%） | 213（47.8%） |
| contradiction | 177 | 230 |

LoCoMoは「No information available」が正解の問にもevidenceターンを付けており、
その指し先は正解に似た**別の**発話である。確実に届けるほどモデルは棄権をやめる。
例: `What country is Melanie's grandma from?`（正解: No information available）は
v40が正しく棄権し、v41は注入された`D4:3`を根拠に`Sweden.`と答えた。

cat5をgold-evidence-onlyの読解基準へ含めるのは不適切である。一方、関連する別事実を渡すと
誤った具体化をして棄権をやめる挙動は実在するため、通常runの副作用・安全指標として残す。
Oracle Readerの主比較にはcat1-4を使う。

## 8. 評価の役割分担

この計画で LoCoMo を使う目的は、本番会話の品質や設定既定を決めることではない。
固定済み会話を同一条件で replay し、記憶パイプラインを段階別に検証することである。

| 評価レイヤー | 主に測るもの | この計画での扱い |
|---|---|---|
| **LoCoMo** | 固定会話からのナレッジ化、検索、注入、回答での利用 | 現在の対象 |
| **AMemGym** | 対話へ参加しながら行う記憶の書き込み・更新・検索・利用 | LoCoMo の次段 |
| **実ユーザー評価** | 現実の会話分布での有用性、安全性、過剰想起 | 別計画・本書の対象外 |

LoCoMo では次の連鎖を一つずつ測る。

```
固定会話 → RAW保存 / カード生成 → 候補検索 → prompt注入 → 回答利用
```

ここでの「ナレッジ化」は、全事実をカード本文へ複製することだけを指さない。
**カードを検索インデックスとして生成し、provenance から必要な原文へ戻れる状態を作ること**も
含む。したがって RAW 注入はカード化の失敗時だけの救済ではなく、カードと原文を役割分担
させる記憶方式として評価する。

AMemGym は、固定履歴を読む LoCoMo では測れない on-policy の対話的評価へ使う。
アシスタント自身の応答を含む会話軌跡の中で、状態変化・訂正・古い記憶との競合を扱えるかを
検証する。AMemGym も構造化状態を持つシミュレートユーザーによる評価であり、実ユーザーでの
外的妥当性はさらに後段である。

- [AMemGym 公式サイト](https://agi-eval-official.github.io/amemgym/)
- [AMemGym ICLR 2026 論文](https://openreview.net/forum?id=sfrVLzsmlf)

本番の `rag_source_mode`、`rag_raw_top_k` の既定変更や既存実インスタンスの移行は、
LoCoMo 上の記憶パイプライン評価とは分離し、この計画の採否条件に入れない。

## 9. LoCoMo 内での失敗分類

現行の `no_card` / `evidence=0` だけでは原因を一意に表せない。今後は少なくとも次へ分ける。

| 分類 | 意味 |
|---|---|
| `raw_missing` | gold evidence が保存済み RAW に無い |
| `card_content_missing` | RAW にはあるがカード本文に事実が残っていない |
| `provenance_missing` | RAW はあるがカードから該当ファイルへ辿れない |
| `retrieval_miss` | 根拠カードが候補 pool に入らない |
| `selection_miss` | 候補にはあるが実際の prompt に根拠が入らない |
| `utilization_miss` | 根拠が prompt に入っているのに回答できない |

主指標は全体スコアだけでなく、RAW1→RAW3で新しく根拠が届いた質問に限定した換算率とする。

```
新規カバーから回答改善への換算率
  = RAW3で改善した質問数 / RAW3で新しく根拠が届いた質問数
```

既に根拠が届いていた質問の改善 / 悪化、`utilization_miss` 率、cat5 の誤利用、prompt tokensも
併記する。cat5 はナレッジ化の主指標ではなく、RAW追加による副作用の監視指標として扱う。

## 10. 今後の方針

優先順は§7.2の診断配分を仮説として置き、各施策の単一変数A/Bで確定する。
まず「原文へ正しく辿り着く」側を試し、渡し方はOracle Bundleで別に残す。

1. ~~**v40を完走し、v37と同一Judge経路で比較する。**~~ 完了（§7）。
2. ~~**gold-evidence-only基準を測る。**~~ 完了（§7.1〜7.4）。cat1-4 0.6258、
   Semantic incorrect 17.0%、段階別の診断配分を得た。
3. **provenance救済を評価する（最優先仮説・診断配分41%）。** 段階1「カードが根拠を指していない」
   205問が単独で最大である。事実が消えているのではなく（§3: archiveに272/279が残存、
   真の欠落は7問）、`source_files`からgold evidenceのファイルへ辿れない。
   `source_files`欠落時に`raw_reference`の日付範囲から候補を復元できるかを検証し、
   正確な生成時provenanceと後付け推定を区別して記録する。
   **判定基準は段階1の問数と、その層のSemanticがOracle基準0.785へどこまで寄るか。**
4. **注入枠とランキングを見直す（診断配分32%）。** 段階3「候補には居るのにtop3へ来ない」173問。
   候補には入っているので検索は当たっており、落ちているのは順位付けと注入枠である。
   [RAG評価・改善レポート](../../history/rag_evaluation_report.ja.md)§5.10でtop-10を不採用にした判断は維持しつつ（promptが+21.8%増えるため）、
   **枠を増やさずに順位を直す**方向——リランカー、Fusion重み、`rag_raw_top_k`との
   組み合わせ——で測る。
5. **multi-hopの必要ターンを揃える（診断配分15%）。** 段階5「一部しか届かない」196問は
   154問がcat1で、必要evidenceが平均3.50ターンある。量不足を主仮説にしつつ、
   Oracle Bundleで粒度・提示形式の影響も分離する。
6. **候補pool側の検索を改善する（診断配分19%）。** 段階2「top20に入らない」115問。
   embedding・検索クエリの領域である。[RAG評価・改善レポート](../../history/rag_evaluation_report.ja.md)§6.5・§6.6に
   候補pool 20→50がRecall@3で最大+1問だった記録があるため、pool拡大ではなくクエリ側を疑う。
7. **段階別の失敗分類を成果物へ追加する。** §7.2の分類を`analyze-evidence`へ組み込み、
   実注入ベース（`raw_reference.files`との突き合わせ）まで含めた
   question-level診断を毎runの成果物にする。v41のquestion-level結果は
   `utilization_miss`候補の補助ラベルとし、純粋な正解ラベルとは扱わない。
8. **Oracle Bundleを比較する（§7.2.1）。** exact goldターンに必要近傍を固定して加え、
   exact-turn Oracleとの差から近傍・提示形式の効果を測る。833問の結果はRAW3 bundleの
   明確な害がないことを示すが、渡し方を解決済みとはしない。
9. **RAW3をLoCoMo上の評価基準として判断する。** 本番既定ではなく、同じナレッジから
   どれだけ根拠を呼び出して利用できるかの比較条件として決める。
10. **LoCoMoの段階評価が安定した後、AMemGymへ接続する。** 同じwrite / read / utilization診断を
    対話中の記憶更新、訂正、状態変化へ拡張する。

v40→v41のcat1-4 +0.17を検索・通常注入側の改善余地を置く診断基準とする（§7.3）。
固定上限ではないため、3〜8の単一変数A/Bで実際に回収できた差を進捗の尺度にする。

カード生成粒度の変更は、`card_content_missing` の実測後に判断する。段階1のOracle基準が
0.785と高いことは原文到達の改善余地を示すが、カード本文の圧縮品質そのものを
測ったわけではないため、現時点では優先度を確定しない。
